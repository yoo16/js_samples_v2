## Cookie とセッションのおさらい

`Web` サーバーはリクエストごとに独立していて、前回のやり取りを覚えていません。この性質を「ステートレス」と呼びます。ログイン状態のように「覚えておきたい情報」を扱うために、`Cookie` とセッションが使われます。

### Cookie とは

`Cookie` はブラウザに保存される小さなデータで、同じサイトへのリクエストのたびに自動的に送信されます。

### セッションIDとは

`PHP` のセッション機能では、`Cookie` にはセッションIDだけを保存し、実際のユーザー情報はサーバー側のセッションデータに保存します。

| 用語 | 内容 |
| ---- | ---- |
| Cookie | ブラウザに保存され、リクエストごとに自動送信される小さなデータ |
| セッションID | ユーザーを識別するためにCookieへ保存するランダムな文字列 |
| セッションデータ | セッションIDに紐づけてサーバー側に保存される情報 |

> `18_secure` では、セッションIDを保存する `Cookie` の名前を `sid` としています。

## HttpOnly 属性とは

`HttpOnly` は `Cookie` に付けられる属性のひとつで、`JavaScript` の `document.cookie` からその `Cookie` を読み書きできないようにします。

### なぜ必要か

サイトに悪意のある `JavaScript` が埋め込まれてしまう攻撃を `XSS`（クロスサイトスクリプティング）と呼びます。もしセッションIDの `Cookie` に `HttpOnly` が付いていないと、`XSS` によってセッションIDを盗まれ、他人になりすまされる危険があります。

**セッションIDのような認証情報の Cookie には、必ず `HttpOnly` を付けます。**

### 設定方法

```php
session_set_cookie_params([
    'httponly' => true, // JSから読み書きできないようにする
]);
```

`HttpOnly` を付けた `Cookie` は、`JavaScript` から見えなくなるだけで、ブラウザからサーバーへのリクエストには引き続き自動的に送信されます。

## セッション固定化攻撃とは

セッション固定化攻撃とは、攻撃者が事前に用意したセッションIDを被害者に使わせ、ログイン後もそのセッションIDで本人になりすます手口です。

### 対策：ログイン時のセッションID再発行

対策として、**ログインが成功したタイミングでセッションIDを発行し直します。**

```php
if ($email === $user['email'] && password_verify($password, $user['hash_password'])) {
    session_regenerate_id(true); // 古いセッションIDを破棄して新しいIDを発行
    $_SESSION['user'] = $user;
}
```

こうすることで、ログイン前のセッションIDが漏れていたとしても、ログイン後のセッションは別のIDに切り替わるため乗っ取りを防げます。

## CSRF とは

`CSRF`（クロスサイトリクエストフォージェリ）とは、ログイン中のユーザーを別のサイトに誘導し、そのユーザーの `Cookie` を利用して意図しないリクエストを送らせる攻撃です。

### CSRF 攻撃の仕組み

`Cookie` はリクエスト先が同じサイトであれば自動的に送信されるため、被害者が悪意のあるページを開いただけで、ログイン中のサイトに対して「本人になりすましたリクエスト」が送られてしまいます。

### CSRF トークンによる対策

`CSRF` トークンは、フォーム送信やログイン処理のたびにサーバーが発行するランダムな文字列です。**サーバーは、リクエストに含まれるトークンとセッションに保存したトークンが一致するかを確認し、一致しない場合は処理を拒否します。**

攻撃者は被害者のセッションに保存された正しいトークンの値を知ることができないため、`CSRF` トークンの検証によって不正なリクエストを防げます。

| 手順 | 内容 |
| ---- | ---- |
| ① 発行 | ページ読み込み時にサーバーがトークンを発行し、セッションに保存する |
| ② 送信 | フォームやAPIリクエストにトークンを含めてサーバーへ送る |
| ③ 検証 | サーバーはセッション内のトークンと送られてきたトークンを比較する |
| ④ 判定 | 一致すれば処理を実行し、不一致なら拒否する |

```php
function require_csrf(): void
{
    $client_token = $_SERVER['HTTP_X_CSRF_TOKEN'] ?? '';

    if (empty($_SESSION['csrf_token']) || !hash_equals($_SESSION['csrf_token'], $client_token)) {
        http_response_code(403);
        echo json_encode(['error' => 'Invalid CSRF token']);
        exit;
    }
}
```

> `CSRF` トークンの検証が必要なのは、ログインやログアウト、投稿、削除のように**状態を変更するリクエスト**だけです。閲覧だけの `GET` リクエストには基本的に不要です。

## CORS とアクセス制御

`CORS`（オリジン間リソース共有）は、あるサイトの `JavaScript` が別のサイトのデータを読み取ってよいかどうかをブラウザが判断するための仕組みです。

### Access-Control-Allow-Origin とは

サーバーが `Access-Control-Allow-Origin` ヘッダーで許可したオリジンだけが、`fetch` や `XHR` のレスポンスを読み取れます。

```php
header('Access-Control-Allow-Origin: *');
```

### 安易に許可してはいけない理由

`*` を指定すると、**すべてのオリジンからのレスポンス読み取りを許可**することになります。ログイン画面のように同一オリジンの `JavaScript` からしか呼び出さない `API` に対してこの設定を入れると、外部サイトにレスポンスの中身を読み取られる余地を作ってしまいます。

> 使う予定のないオリジンにまで `CORS` を開放するのは避けます。「必要な範囲だけ許可する」が基本方針です。

## まとめ

| 用語 | 内容 |
| ---- | ---- |
| HttpOnly | JavaScriptからCookieを読み書きできないようにする属性。XSS対策 |
| セッション固定化攻撃 | 攻撃者が用意したセッションIDを被害者に使わせて乗っ取る攻撃 |
| session_regenerate_id | ログイン成功時にセッションIDを再発行し、固定化攻撃を防ぐ関数 |
| CSRF | ログイン中のユーザーに意図しないリクエストを送らせる攻撃 |
| CSRFトークン | セッションに保存し、リクエストごとに照合する使い捨てのランダム文字列 |
| CORS | 別オリジンのJavaScriptにレスポンスを読ませてよいかをブラウザが判断する仕組み |
